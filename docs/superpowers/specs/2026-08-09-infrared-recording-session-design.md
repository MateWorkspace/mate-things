# Infrared recording session design

Date: 2026-08-09

## Context

`internal/domain/models/infrared.go` already defines the device/state taxonomy for the
Smart IR system being absorbed into mate-things (`InfraredDeviceType`, `InfraredDevice`,
`InfraredState`, `InfraredStateDeviceDefinition`) and a first pass at the recording
pipeline (`InfraredStateDeviceRecordCase`, `RecordState`, `RecordRaw`) and the derived
encoding artifact (`InfraredStateDeviceResult`, `ResultBit`).

Prior discussion (not written up until now) settled the following, which this design
builds on directly:

- **Case set stays deterministic.** Cases are a one-factor-at-a-time (OFAT) sweep from a
  fixed baseline over `InfraredState` × `InfraredStateDeviceDefinition`, generated by
  plain Go enumeration. This preserves clean per-state bit attribution: each case differs
  from baseline in exactly one state, so any bit that changes is attributable.
- **LLM's role is judgment and language, not case selection.** The LLM writes the
  human-facing recording instructions and picks a press-order that minimizes physical
  button presses; it does not decide which state combinations exist as cases.
- **Deterministic bit-analysis still runs before the LLM writes any code.** Frame
  segmentation, volatile-bit detection (via required duplicate captures per case),
  checksum discovery (via intersection of per-state deltas), and per-state bit
  attribution all happen in Go. Their output is context for the LLM, never shown to
  staff directly.
- **The LLM generates code, not a declarative document.** Earlier discussion considered
  a JSON document as the primary encoding artifact; that's superseded here in favor of
  an LLM-generated JavaScript encoder/decoder pair, executed via `goja` on the backend.
  This is viable specifically because recording is staff-only (not user-submitted), so
  the code-injection concerns that would rule this out for user-supplied protocols don't
  apply — the write path is admin/staff-gated the same way the rest of this pipeline is.
- **Hardware is the verification authority, not automated round-trip.** Generated
  encoders are verified by actually transmitting to a physical AC and having staff
  confirm the result, not by round-tripping against recorded bytes (which mostly
  confirms checksum validity, not field semantics).
- **A device can have recording history.** `InfraredDevice` to recording effort is 1:N.
  Only one result is "active" (in use) per device at a time; earlier ones are retained
  as history.

## Goals

- Track a full recording effort — from form submission through case recording, encoder
  generation, and hardware-verified testing — as one auditable `InfraredRecordSession`.
- Support retry at two grains: a single bad capture (staff misclick) and a whole failed
  test case (encoder needs more data), without losing prior work or history.
- Keep the LLM's role bounded to what it's actually good at: natural-language
  instructions, ordering, and judgment calls on ambiguous analysis results — never
  case existence, never unverified claims of correctness.

## Non-goals

- Decoder verification. `InfraredStateCoder.DecoderSource` is generated alongside the
  encoder (same LLM call, same analysis context) but is not exercised by this recording
  flow's test loop. It stays `UNVERIFIED` in practice until some future feature
  consumes it.
- Automated interaction detection across all state pairs. Only one supplementary
  baseline (a second sweep of the states most likely to interact with the primary
  discriminant, typically the ones most affected by `MODE`) is in scope; this design
  doesn't add exhaustive pairwise coverage.
- Any change to how `InfraredDeviceType` / `InfraredState` /
  `InfraredStateDeviceDefinition` are authored — those remain plain user/staff-entered
  data, unchanged by this design.

## Session lifecycle

```
DRAFT → CASES_GENERATING → RECORDING → ANALYZING → FUNCTION_GENERATING
  → TEST_CASES_GENERATING → TESTING ─┬─ all pass → COMPLETED
                                     └─ any fail → RECORDING (loop, new cases appended)

any active state → FAILED (staff abandons the session)
```

- `DRAFT → CASES_GENERATING`: triggered by submitting the recording form (device type,
  brand, model, node, state definitions). Creates `InfraredDevice`, `InfraredRecordSession`,
  and `InfraredStateDeviceDefinition` rows together.
- `CASES_GENERATING → RECORDING`: Go enumerates the deterministic OFAT case set and
  writes `RecordCase`/`RecordState` rows; the LLM then fills in each case's
  `Description` (human instruction, stating the *full* target state, not just the
  delta) and re-orders `Step` to minimize button presses.
- `RECORDING`: staff works through cases in `Step` order, tracked by
  `InfraredRecordSession.CurrentRecordCaseId`. Each case needs 2 accepted raw captures
  (for volatile-bit/clock detection) before it's `ACCEPTED`; the cursor then advances to
  the case with the next-higher `Step` (or to `null`, once none remain, which is what
  triggers `RECORDING → ANALYZING`).

  `Step` is append-only and monotonic for the lifetime of the session — the initial
  enumeration takes `1..N`, and any later round of cases appended after a test failure
  takes `N+1..N+k`, and so on. Steps are never renumbered or reused. This is what makes
  `CurrentRecordCaseId` an unambiguous, cheap-to-update cursor across retry rounds, and
  makes "last accepted case" a stable query (`... WHERE Status = 'ACCEPTED' ORDER BY
  Step DESC LIMIT 1`) without needing to track which round a case belongs to separately.
- `ANALYZING` (internal, no staff step): deterministic Phases 0–4 — frame segmentation,
  volatile-bit detection, checksum discovery via delta-intersection, per-state bit
  attribution. Output is an internal payload (template, volatile mask, checksum
  hypothesis, per-state placement/values), not persisted as its own table — it's
  ephemeral input to the next stage.
- `FUNCTION_GENERATING`: the analysis payload plus the device's state/definition list
  goes to the LLM, which returns `EncoderSource`, `DecoderSource`, and the two README
  fields, persisted as a new `InfraredStateCoder` row with `Status: UNVERIFIED`.
- `TEST_CASES_GENERATING`: the LLM receives the finished encoder and the state/definition
  list and proposes a minimal-but-sufficient set of `InfraredTestCase` rows — its own
  judgment about which combinations best exercise the encoder, not necessarily the same
  set as the recording cases.
- `TESTING`: for each test case, the backend runs `EncoderSource` against the declared
  state, transmits the result via the session's `Node`, and staff marks the case
  `PASSED`/`FAILED` after observing the physical unit.
  - All `PASSED` → `COMPLETED`. The `InfraredStateCoder` row flips to `ACTIVE`; any
    prior `ACTIVE` coder for the same device flips to `SUPERSEDED`.
  - Any `FAILED` → back to `RECORDING`. New targeted `RecordCase` rows are appended to
    the *same* session (nothing is deleted); re-running analysis and generation produces
    a *new* `InfraredStateCoder` row rather than editing the failed one, preserving full
    history of every generation attempt within the session.
- `FAILED`: manual, staff-initiated abandonment from any active state. Nothing
  auto-fails a session.

## Retry semantics

Two distinct grains, both explicit rather than inferred:

- **Single bad capture (misclick):** staff marks the specific
  `InfraredStateDeviceRecordRaw` `DISCARDED` with a reason and recaptures. The case
  stays `ACTIVE`; only the discarded raw is excluded from analysis.
- **Whole case recorded against the wrong physical state:** staff marks the case back
  to `ACTIVE`, which discards its existing `ACCEPTED` raws (with reason) so there is
  never more than one valid capture pair per case at a time — the analyzer never has to
  choose between ambiguous "most recent" raws.
- **Failed test case:** session returns to `RECORDING` with new `RecordCase` rows
  appended to the same session (never a new session, never deleting prior cases), taking
  the next available `Step` values per the monotonic rule above.
  `CurrentRecordCaseId` is set to the first of the newly appended cases. Re-analysis and
  re-generation produce a new `InfraredStateCoder` row, so every generation attempt
  within a session remains inspectable.

## Sanity-checking captures in flight

Before a raw capture is presented to staff for accept/discard, the backend compares its
frame signature (frame count + per-frame bit length) against the set of signatures
already accepted as valid within the session (initially just the baseline case's
signature). A mismatch against that known-good set is flagged for staff attention rather
than silently accepted — this catches a garbled or wrong-button capture immediately
rather than waiting for a later capture to reveal the discrepancy. The first case whose
signature legitimately differs from baseline (e.g. a shorter `POWER=OFF` frame) requires
one manual confirmation; after that its signature joins the accepted set for the rest of
the session.

## Open items for the implementation plan

- Exact `goja` invocation contract for `EncoderSource` (function signature, execution
  timeout, how the resulting timing array is validated before being sent to a `Node`).
- How `InfraredTestCase` failures translate into which new `RecordCase` rows get
  generated — likely an LLM call given the failing test case's declared state and the
  current coder's README/analysis context, but the exact prompt contract isn't decided.
- Whether the deterministic Phase 0-4 analysis payload should be persisted anywhere
  (even transiently) for debugging a bad generation, or purely computed in-memory per
  the "internal, no staff step" framing above.
- MQTT topic/message shape for both directions (receive during `RECORDING`, transmit
  during `TESTING`) — not addressed here, belongs in the implementation plan.
